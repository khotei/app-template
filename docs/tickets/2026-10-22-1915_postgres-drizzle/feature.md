# Postgres and Drizzle

> Ticket: `2026-10-22-1915_postgres-drizzle` · Source:
> [roadmap › 4](../../knowledge/roadmap.md#4-postgres-drizzle), grilling on 2026-10-22
> Related: [architecture.md](./architecture.md) · [plan.md](./plan.md)

## Goal

Users, chats, messages and attachment records move from the file-backed `KeyValueStore` to
Postgres through Drizzle's Effect integration over `@effect/sql-pg`, so that the api and the
worker share one database and a second api process is safe. A send becomes one transaction that
also writes its jobs to an outbox, which the worker relays to SQS: a message can no longer exist
without its job, and a chat can no longer stay busy or untitled because an enqueue failed after a
write. The database's own guards (a partial unique index, conditional updates) replace the
in-process `UserLock`. Locally the database is an RDS instance on MiniStack created by
`@pulumi/aws`, the first use of the AWS provider against the local stand; tests run on a real
Postgres, one container per run.

## Context

- **Starting point.** `chat-core` (3) and `aws-local` (5) merged. The repositories
  (`UserRepositoryKv`, `ChatRepositoryKv`, `MessageRepositoryKv`, `AttachmentRepositoryKv`) run on
  `KeyValueStore.layerFileSystem` at `STORE_PATH` through `infrastructure/kv`; attachment bytes
  are in S3 (`AttachmentStoreS3`), jobs on SQS (`QueueClientSqs`). `SendMessageUseCase.send`
  runs under `UserLock.withPermit` and writes in this order: check (`findSendable`,
  `findBindable`), user message, binds, assistant message, chat `updatedAt`, then
  `AssistantMessageJob.enqueue` and, for a chat's first message, `ChatTitleJob.enqueue`. A failure
  after a write leaves a `queued` message with no job (the chat busy for good) or a chat with no
  title job. Both job handlers are idempotent (`alreadySettled`, `alreadyTitled`). The local
  stand is the Pulumi project `deployment/local/` (Docker provider, MiniStack by digest, `.data/`
  for state); `deployment/aws/` is a stub.
- **Inherited from `aws-local`** ([roadmap › 4 › Inherits](../../knowledge/roadmap.md#4-postgres-drizzle)):
  - a guard on the reply's stage writes: taken as `WHERE stage = <the stage read>` (R12);
  - a consumer or sweep for replies left active in the dead-letter queue: taken as a consumer of
    `assistant-message-dlq` (R13);
  - a sweep of expired unbound attachment records: declined (see Out of scope); the rows stay,
    read as not found.
- **Decided in grilling (2026-10-22).**
  - The whole store moves; `infrastructure/kv`, `KeyValueStoreFileSystem`, `STORE_PATH` and
    `.data/store` go. No test double keeps a KV implementation alive: every test that needs a
    repository runs on Postgres.
  - The domain stays the source of truth: `Schema.Class` models, `MessageStage` and
    `MessageAuthor` literals, ids and timestamps are unchanged, and the HTTP contract with them.
    Drizzle tables live in `infrastructure/<aggregate>/<entity>.entity.ts` and mirror the models;
    `drizzle-orm/effect-schema` derives row schemas inside the adapter only.
  - Tables and columns are `snake_case` in the database (`snakeCase.table` from
    `drizzle-orm/pg-core`), `camelCase` in code. Shared column sets (`id`, timestamps) are
    declared once, as Drizzle's schema docs advise.
  - Time and ids belong to the domain: `createdAt` and `updatedAt` are written with the values the
    domain takes from `Clock`, with no `$onUpdate` and no `DEFAULT now()`; ids stay UUIDv7 from
    `Crypto`, and `DEFAULT uuidv7()` on `id` is a fallback for hand-written SQL only. The
    roadmap's `$onUpdate` item is dropped.
  - The bind is the only link between a message and its attachments (`attachments.message_id`,
    a foreign key); the message keeps no copy of the list. A message's attachments read in
    upload order (`created_at`, then `id`), not in the order the send listed them: a send of
    `[C, A]` after uploading A, B, C reads back as `[A, C]`. The `202` of
    `POST /chats/:chatId/messages` lists the attachments the bind returns, in the request's
    order, while a later read returns upload order.
  - Outbox with a relay only: no eager publish from the api. The relay runs in the worker and
    polls at a configurable interval, default 1 s.
  - `UserLock` is removed; the transaction, a partial unique index and conditional updates are
    the guards.
  - Stuck replies: the worker consumes `assistant-message-dlq` and writes the same message
    `failed` with the existing reason `ReplyFailed`, the cause naming the dead-letter queue; no
    new reason, no contract change. `chat-title-dlq` is logged only.
  - Expired unbound attachment rows are not swept: the bucket rule deletes the bytes on AWS, the
    rows stay and read as not found. A later script or job may remove them.
  - Migrations are SQL files generated by `drizzle-kit generate` and committed; only
    `make migrate` (called by `make up`) and the test setup apply them, through
    `drizzle-orm/effect-postgres/migrator` in an Effect program that reads `DatabaseConfig`. The
    apps never migrate or check the schema at startup. `drizzle.config.ts` holds `dialect`,
    `schema` and `out` only; `drizzle-kit push`, `migrate` and `studio` are not used. The
    production migration command waits for `aws-deployment` (9).
  - The local database is an RDS instance on MiniStack created with `@pulumi/aws`, since that
    is the direction of `aws-deployment` (9); the bucket and the queues move into the same
    Pulumi program, which replaces `deployment/local/provision.ts`.
  - `DATABASE_URL` is a stack output in `.env.pulumi`, not in `.env`; a worktree sets its own
    `RDS_BASE_PORT` and `STAGE`.
  - `make down` keeps the data (`RDS_PERSIST=1`); `make reset` removes it, container and volume
    included. Neither runs `pulumi destroy`.
  - SQL is logged at `Debug` only, through a small `EffectLogger` layer of our own (Drizzle's
    `EffectLogger.layer` logs at `Info`); Drizzle's cache stays `EffectCache.Default`.
  - Tests: one Postgres container per `vitest` run, a template database migrated once, a fresh
    database per test created from the template; only the queue suite runs on MiniStack, in a
    container of its own (`architecture.md › D21`).
  - Catalogs: `drizzle-orm` and `drizzle-kit` `1.0.0-rc.5` in a new `drizzle` namespace (one
    release train); `@effect/sql-pg` in `effect`; `@testcontainers/postgresql` in `runtime`.

## Scope

- Drizzle tables and row schemas per aggregate (`user`, `chat` with `message`, `attachment`,
  the outbox), the Postgres repositories implementing the domain ports, the `PgClient` layer
  from `DatabaseConfig`, the migrations folder and the `migrate` program.
- The transactional send with the outbox and the relay in the worker.
- The database guards that replace `UserLock`: one active message per chat, a bind only while
  unbound, single-statement `touch` and `rename`; conditional stage writes.
- The dead-letter consumer for replies.
- The local stand on Pulumi: `@pulumi/aws` `rds.Instance`, the bucket and the queues inside
  MiniStack (the Docker socket, `RDS_BASE_PORT`, `RDS_PERSIST`), `DATABASE_URL` in `.env.pulumi`;
  `make migrate`, `make migration NAME=<name>`, `make up`, `down`, `reset` reworked.
- Tests on Postgres: the shared container, the template database, a database per test.
- Removal of `infrastructure/kv`, `UserLock`, `STORE_PATH`; `docs/knowledge/database.md`.

## Out of scope

- AWS resources for the database and the production migration command: `aws-deployment` (9).
- A sweep of expired unbound attachment rows: declined; a later script or job may remove them.
- Moving the MiniStack suites to one container per run: a note for a later ticket.
- `drizzle-kit push`, `migrate` and `studio`; Drizzle's query cache. *Amended in architecture
  (D6): Drizzle relations are in, for the read models behind `ChatRepository`.*
- Observability of the database (query spans, pool metrics): `observability` (8).
- Data migration from `.data/store`: dev data is disposable.
- An SSE tail or any change to the HTTP contract.

## Requirements

### Persistence

- **R1** — WHEN the api or the worker starts, THE SYSTEM SHALL read and write users,
  credentials, chats, messages and attachment records in the Postgres database at
  `DATABASE_URL`, and SHALL hold no record in a key-value store.
- **R2** — THE SYSTEM SHALL serve the same HTTP contract as before: the routes, statuses and
  bodies of the `HttpApi` in `http-api/` are unchanged, and every `chat-core` and `aws-local`
  requirement that the api and the worker meet today still holds, save that a send's user message
  and its reply, which share `createdAt`, read back in either order (`chat-core` R7, R17).
  *Amended in S6:* the api no longer serves `/openapi.json` or `/docs`, which no client reads, so
  the contract is the `HttpApi`, not a byte-identical document (D20); the pair's order is left
  undefined (D19).
- **R3** — THE database SHALL name tables and columns in `snake_case` while code uses `camelCase`;
  each aggregate's tables SHALL be declared in `infrastructure/<aggregate>/<entity>.entity.ts`
  (one file per entity, as its repositories are split: `chat.entity.ts`, `message.entity.ts`) from
  the domain's literals (`pgEnum` over `MessageStage`, `MessageAuthor`); ids SHALL be `uuid`
  primary keys with `DEFAULT uuidv7()` as a fallback, and `createdAt`/`updatedAt` `timestamptz`
  columns written with the domain's values, never by a database default or trigger.
- **R4** — WHEN a record is read back, THE SYSTEM SHALL return the domain model it was written
  from (`Option`, `DateTime.Utc`, brands and literals intact), including `MessageFailure` with
  its `cause`, save that a message's `attachmentIds` read in upload order.

### The transactional send

- **R5** — WHEN `POST /chats/:chatId/messages` succeeds, THE SYSTEM SHALL commit the user
  message, its binds, the assistant message, the chat's `updatedAt` and the outbox entries of its
  jobs (the reply; the title when the message opens the chat) in one transaction.
- **R6** — IF any write of the send fails, THEN THE SYSTEM SHALL leave no message, bind, chat
  change or outbox entry behind, and no job SHALL reach SQS.
- **R7** — WHILE outbox entries are pending, THE worker SHALL publish each to the SQS queue of
  its definition within the relay interval (`OUTBOX_POLL_INTERVAL`, default 1 s) and delete it;
  IF a publish fails, THEN the entry SHALL stay pending and be retried on the next poll.
  *Amended in S10:* a sent entry is deleted, not marked (D4).
- **R8** — WHEN several relays run (two worker processes), THE SYSTEM SHALL hand a pending entry
  to one of them at a time (`FOR UPDATE SKIP LOCKED`); a crash between the publish and the commit
  MAY publish the entry once more, which the idempotent handlers absorb (`aws-local` R9).

### Guards in place of `UserLock`

- **R9** — WHEN two sends to the same chat run concurrently, in one api process or in two, THE
  SYSTEM SHALL complete exactly one and answer the other `409 ChatBusyError`, storing nothing
  for it (`chat-core` R12): the database SHALL allow at most one active assistant message per
  chat.
- **R10** — WHEN two sends bind the same attachment concurrently, THE SYSTEM SHALL complete
  exactly one and answer the other as `chat-core` R13 does: a bind SHALL succeed only while the
  attachment is unbound.
- **R11** — WHEN a rename and a send, or a send and the title job, change the same chat
  concurrently, THE SYSTEM SHALL keep both changes (the title and the `updatedAt`), and THE
  application SHALL hold no in-process lock across a check and a write.

### Stage writes and stuck replies

- **R12** — WHEN the worker moves an assistant message to another stage, THE SYSTEM SHALL write
  it only where the stored stage is still the one the job read (`WHERE id = … AND stage = …`); IF
  no row matches, THEN the job SHALL treat the message as settled by someone else and skip, as it
  does today for a terminal message. *Amended in S7:* the guard is the stage read, not the stages
  the transition allows, which would let a stale attempt fail a reply another attempt is writing;
  two attempts both in `generating` are not told apart (D5).
- **R13** — WHEN a reply job arrives on `assistant-message-dlq`, THE worker SHALL consume it and,
  IF the message is still active, write it `failed` with reason `ReplyFailed` and a cause naming
  the dead-letter queue and the attempts spent, and move the chat's `updatedAt`; IF the message is
  terminal or the chat is gone, THEN it SHALL log the skip and write nothing. WHEN a title job
  arrives on `chat-title-dlq`, THE worker SHALL log it and write nothing.

### Migrations and configuration

- **R14** — THE schema SHALL change only through SQL migrations generated by `drizzle-kit
  generate` (`make migration NAME=<name>`, no database needed) and committed; `make migrate`
  SHALL apply the pending ones through an Effect program that reads `DatabaseConfig`, and SHALL
  change nothing when none is pending; the apps SHALL neither migrate nor check the schema at
  startup.
- **R15** — THE SYSTEM SHALL read the database settings only through `DatabaseConfig` in
  `@app-template/config`, from the single variable `DATABASE_URL`, which `make up` writes to
  `.env.pulumi` as a stack output and which `.env.example` does not list; `STORE_PATH` SHALL be
  gone from code, `.env.example` and docs.

### The local stand

- **R16** — WHEN `make up` runs, THE SYSTEM SHALL provide a Postgres 18 database as an RDS
  instance that the Pulumi program of `deployment/local/` creates inside MiniStack through
  `@pulumi/aws`, beside the inventory's bucket and queues, on the host port `RDS_BASE_PORT`
  (`15432 + 10N` for worktree `N`), SHALL write its `DATABASE_URL`, a stack output, to
  `.env.pulumi`, which the apps and `make migrate` load after `.env`, and SHALL apply the
  migrations to it. A second `make up` SHALL change nothing.
- **R17** — WHEN `make down` runs, THE SYSTEM SHALL stop the stand and keep the database's data
  and port for the next `make up`; WHEN `make reset` runs, THE SYSTEM SHALL remove the data, the
  database container and its volume together with `.data/` and `.env.pulumi`.
- **R18** — WHILE several worktrees run, THE SYSTEM SHALL keep their databases apart: a different
  port and container per tree, as for MiniStack today.

### Logging

- **R19** — WHILE `LOG_LEVEL` is `Debug`, THE SYSTEM SHALL log every SQL statement with its
  parameters through Effect's logger; at `Info` and above it SHALL log no statement.

### Tests

- **R20** — WHEN `make test` runs, THE SYSTEM SHALL start one Postgres container for the run,
  migrate one template database once, and give every test that needs a database a fresh database
  created from the template and dropped when the test ends, so that no test sees another's rows
  and files run in parallel, and no test depends on `.env` or on `make up`; `make test` SHALL need
  Docker and nothing else.
- **R21** — THE repository, service, use case, job and api suites SHALL run on the Postgres
  layers the apps use, with no in-memory repository, and SHALL cover R5–R13 at the seams
  `architecture.md` names.

### Documentation

- **R22** — THE SYSTEM SHALL document the database in `docs/knowledge/database.md` (schema and
  entity files, the transaction and the outbox, the guards, migrations, the local RDS, tests),
  link it from `architecture.md`, and update `tooling.md` (targets, catalogs, worktree ports,
  `.env.pulumi`), `aws.md` (the local stand on Pulumi: MiniStack, the RDS instance, the bucket
  and the queues) and
  `naming.md` (`.entity`).

## Open questions

- **The transaction boundary in `application`.** How a use case says "all of this commits
  together" without importing `@effect/sql`: a domain port (`Transaction` or `UnitOfWork`) whose
  Postgres layer is `SqlClient.withTransaction`, relying on `@effect/sql` carrying the
  transaction in the Effect context so the repositories join it; and whether Drizzle's
  `db.transaction` or `SqlClient.withTransaction` is the one the adapters use.
- **Where the `rds.Instance` lives.** Closed in S3: in the one program of `deployment/local`,
  beside MiniStack; `make down` is `docker stop`, so no destroy reaches it (`architecture.md ›
  D11`). The provider needs `endpoints` and the three skip flags, and MiniStack nothing more.
- **Where the outbox lives.** Its entity and the relay: `infrastructure/outbox/` with the relay
  as a worker layer in `application/`, or beside the jobs; how a job's `enqueue` becomes an
  outbox insert inside the send's transaction while the job class keeps its `worker`.
- **How `ChatBusyError` arises.** The check inside the transaction and the unique violation
  (`23505`) on the partial index both have to map to it; which error the use case sees under
  `READ COMMITTED`.
- **Timestamps on the wire.** Drizzle's docs configure `PgClient` so timestamp types arrive raw;
  what `@effect/sql-pg`'s type registry does by default and whether `mode: 'date'` or a string
  column with a `DateTime.Utc` codec is the cleaner mapping.
- **Deleting a chat.** Foreign keys with `ON DELETE CASCADE` or the explicit steps of today
  (attachments first, so a retry finishes the cascade), given the bytes in S3 are not in the
  transaction.
- **The test database plumbing.** How the URL of each test's own database reaches the test under
  vitest 5 on Bun (`globalSetup` with `provide`, or an environment variable), and how the template
  database is built once per run.
- **Repository ports.** Whether `selectByUser` returns sorted (`ORDER BY updated_at DESC`) and
  `selectActiveByChat` uses the partial index, which changes the ports' doc comments.
